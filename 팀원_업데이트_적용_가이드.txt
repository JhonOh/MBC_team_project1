어딧세이 팀원 업데이트 적용 가이드
작성 기준: 2026-10-06
대상: 기존 프로젝트와 odysay.db를 가지고 있는 팀원
명령어 기준: Windows PowerShell

============================================================
0. 먼저 알아둘 내용
============================================================

GitHub에서 코드를 받아도 각자 컴퓨터의 DB는 자동으로 바뀌지 않습니다.
코드는 프로그램이고, odysay.db는 회원·게시글·찜·문의 등을 저장한 파일입니다.

이번 변경에는 내 글/찜 목록, 최근 글, 비공개 문의와 관리자 답변,
통합 검색과 자동완성, 지도와 헤더 수정이 포함됩니다.

모든 팀원에게 오류가 반드시 생기는 것은 아닙니다.
각자의 DB 구조, 적용된 업데이트, 설정에 따라 결과가 다릅니다.

이 가이드에서는 .gitignore 내용을 수정하지 않습니다.
필요한 마이그레이션 파일만 git add -f로 공유합니다.
아래 명령은 안내입니다. 이 문서를 만드는 과정에서 실행하지 않았습니다.

[중요]
현재 마이그레이션을 모든 팀원 DB에서 검증한 것은 아닙니다.
공유자는 먼저 1번 준비 작업을 끝내야 합니다.
팀원은 공유자의 적용 가능 확인을 받은 뒤 DB 업데이트를 실행하세요.

============================================================
1. 코드를 GitHub에 올리는 사람이 먼저 할 일
============================================================

1-1. 필요한 마이그레이션 파일만 Git에 추가하기

현재 .gitignore에는 migrations/가 있어 일반 git add로는 새 파일이
추가되지 않습니다. .gitignore는 그대로 두고 다음을 실행합니다.

git add -f migrations/alembic.ini migrations/env.py migrations/script.py.mako
git add -f migrations/versions/*.py

추가할 목록을 확인합니다.

git diff --cached --name-only -- migrations

설정 파일과 versions 폴더의 Python 파일들이 보여야 합니다.
__pycache__, DB, 백업 파일을 강제로 추가하지 마세요.
git add -f . 처럼 프로젝트 전체를 강제로 추가하면 안 됩니다.

참고: -f는 .gitignore 파일을 수정하지 않습니다.
다만 한 번 등록된 파일은 이후에도 Git이 변경을 추적합니다.
새 마이그레이션 파일은 계속 무시되므로, 새로 만들 때마다 해당 파일을
git add -f로 추가해야 합니다.

마이그레이션을 Git에 아예 올리지 않는 정책이라면 이 명령은 사용하지
마세요. 그 경우 같은 버전의 마이그레이션 파일을 별도로 전달해야 하며,
팀원이 코드와 DB 업데이트 파일을 모두 받았는지 확인해야 합니다.

1-2. 마이그레이션 충돌 확인하기 [공유 전 필수]

확인 당시 최신 파일:
migrations/versions/e9eaa2cbb506_add_inquiries_table.py

이 파일은 다음 변경을 함께 수행합니다.
- inquiries 테이블 생성
- review_recommends 테이블 생성
- travel_talk_recommends 테이블 생성
- travel_talk_comments.parent_id 컬럼 추가

팀원 DB에 위 항목이 이미 있으면 table already exists 또는
duplicate column name 오류가 날 수 있습니다.

공유자가 해야 할 일:
1) 팀원별 db current 결과를 확인합니다.
2) 업데이트 대상 테이블과 컬럼이 이미 있는지 확인합니다.
3) 팀원 DB의 복사본에서 업그레이드를 검증합니다.
4) 중복 항목은 구조가 같은지 확인한 후 처리 방법을 정합니다.
5) 검증된 명령과 예상 최신 리비전을 팀원에게 공지합니다.

기존 리비전 번호를 임의로 바꾸거나 파일을 지우지 마세요.
이미 적용된 DB가 있기 때문에 마이그레이션 수정은 팀 공통으로 관리해야 합니다.

확인 당시 로컬 DB의 리비전과 코드의 head는 e9eaa2cbb506입니다.
이후 마이그레이션을 추가했다면 새로운 head를 기준으로 공지하세요.

updated_at 컬럼 보정은 repair_udated_at.py로 별도 수행한 이력이 있습니다.
현재 문의 마이그레이션만으로 해당 컬럼까지 모두 보정되지는 않습니다.
관리 테이블도 admin-init-db로 별도 생성하는 구조입니다.
따라서 db upgrade만으로 모든 팀원 DB가 완성된다고 가정하면 안 됩니다.

1-3. 최신 코드와 새 파일을 빠짐없이 추가하기

git add odysay repair_udated_at.py
git add -- "팀원_업데이트_적용_가이드.txt"
git status --short
git diff --cached --stat

AM은 추가한 파일을 다시 수정한 상태입니다.
같은 파일을 다시 git add 해야 마지막 수정까지 커밋됩니다.
??는 아직 Git에 추가하지 않은 파일입니다.

특히 확인할 파일:
- odysay/templates/mypage_my_bookmarks.html
- odysay/services/search_service.py
- odysay/views/a6_inquiry_veiws.py
- odysay/views/a7_search_views.py
- odysay/templates/components/header_search.html
- odysay/templates/search_results.html
- odysay/static/js/header_search.js
- odysay/static/css/header_search.css
- 문의 관련 템플릿과 CSS
- migrations 설정 및 versions 폴더의 전체 이력
- repair_udated_at.py

파일명 a6_inquiry_veiws.py와 repair_udated_at.py는 현재 실제 이름입니다.
철자를 임의로 고쳐 쓰면 파일을 찾지 못할 수 있습니다.

검증과 변경 목록 검토가 끝나면 팀에서 사용하는 브랜치로 커밋하고
푸시/PR 절차를 진행하세요. 이 가이드는 브랜치 이름을 정하지 않습니다.

============================================================
2. 팀원이 업데이트를 적용하는 순서
============================================================

[시작 조건]
공유자가 1-2의 DB 업그레이드 검증을 완료했다고 알려준 뒤 진행하세요.
새로 설치하는 사람이나 DB가 없는 사람은 이 기존 DB용 절차를 그대로
진행하지 말고, 별도의 초기 설치 절차를 요청하세요.

2-1. 실행 중인 Flask 서버 끄기

서버가 실행 중인 터미널에서 Ctrl+C를 누릅니다.

2-2. 프로젝트 폴더로 이동하기

cd D:\PGH\flask_web_project-main

폴더가 다른 곳에 있으면 자신의 경로로 바꾸세요.

Get-ChildItem

odysay 폴더, config.py, requirements.txt가 보이는지 확인합니다.

2-3. DB 백업하기

Copy-Item .\odysay.db -Destination ("odysay_before_update_" + (Get-Date -Format "yyyyMMdd_HHmmss") + ".db")

odysay_before_update_날짜_시간.db 파일이 생기면 성공입니다.
원본 DB가 없다는 오류가 나오면 여기서 멈추고 팀에 알려주세요.

2-4. 내 작업 상태 확인하기

git status
git branch --show-current

수정 중인 파일이 있다면 먼저 본인 작업을 보관하거나 커밋합니다.
팀에서 합의한 업데이트 대상 브랜치인지 확인한 뒤 실행합니다.

git pull --ff-only

충돌이나 fast-forward 오류가 나오면 멈추고 팀에 공유합니다.
자기 작업을 지우는 git reset --hard로 강제 해결하지 마세요.

2-5. 패키지 설치하기

.\.venv\Scripts\python.exe -m pip install -r requirements.txt

가상환경 Python을 직접 지정하므로 별도로 활성화할 필요는 없습니다.
.venv가 없다면 기존 개발 환경의 위치부터 확인하세요.
No matching distribution found 등이 나오면 실패한 패키지와 로그를 공유합니다.
임의로 버전을 바꾸지 마세요.

2-6. 환경 설정 확인하기

.\.venv\Scripts\python.exe setup_env.py

.env가 없으면 생성하고, 이미 있으면 덮어쓰지 않습니다.
기존 .env의 SECRET_KEY가 빈 값이나 dev라면 별도로 안전한 값으로 설정해야 합니다.
예를 들어 아래 명령으로 새 값을 생성해 자신의 .env에 저장할 수 있습니다.

.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_hex(32))"

.env에는 SECRET_KEY=생성된값 형태로 저장합니다.
키를 바꾸면 기존 로그인 세션이 무효화될 수 있으므로 다시 로그인하세요.
키와 .env 내용은 GitHub나 단체 채팅에 공유하지 않습니다.
각자 필요한 외부 API 키는 자신의 값을 사용합니다.

2-7. DB 버전 확인하기

.\.venv\Scripts\python.exe -m flask --app odysay:create_app db heads
.\.venv\Scripts\python.exe -m flask --app odysay:create_app db current

heads는 받은 코드의 최신 DB 버전입니다.
current는 내 DB에 기록된 버전입니다.
Can't locate revision, KeyError 또는 예상하지 못한 빈 결과가 나오면 중단합니다.
공유자가 확인한 리비전과 다르면 업그레이드 전에 알려주세요.

2-8. DB 업데이트하기

공유자가 내 DB 상태에서도 적용 가능하다고 확인했을 때만 실행합니다.

.\.venv\Scripts\python.exe -m flask --app odysay:create_app db upgrade

에러가 없을 때만 다음 명령으로 넘어갑니다.

.\.venv\Scripts\python.exe repair_udated_at.py

수정일 컬럼이 없으면 추가하고, 이미 있으면 건너뜁니다.
정상 완료 메시지: 완료: 모든 변경 사항을 저장했습니다.

.\.venv\Scripts\python.exe -m flask --app odysay:create_app admin-init-db

이 명령은 DB를 백업하고 관리자 관련 테이블이 없을 때 생성합니다.

마지막으로 버전을 확인합니다.

.\.venv\Scripts\python.exe -m flask --app odysay:create_app db current

공유자가 공지한 최신 리비전과 일치해야 합니다.
단, 리비전 일치만으로 모든 컬럼이 정상이라는 뜻은 아니므로 기능 확인도 필요합니다.

2-9. 관리자 계정 설정하기 [관리자 기능 테스트 시]

자신의 DB에 있는 관리자용 회원 ID를 확인합니다.
.env에 다음 형식으로 넣습니다.

ADMIN_USER_ID=실제숫자

예시 문구를 그대로 넣지 말고 실제 회원 ID 숫자로 바꾸세요.
다른 사람 DB의 ID를 그대로 복사하면 다른 계정이 관리자가 될 수 있습니다.

.\.venv\Scripts\python.exe -m flask --app odysay:create_app admin-check

출력된 계정이 의도한 계정인지 확인합니다.
일반 사용자 기능만 쓰는 사람은 관리자 지정이 필수는 아닙니다.

2-10. 서버 실행하기

.\.venv\Scripts\python.exe -m flask --app odysay:create_app run

브라우저로 접속하고 Ctrl+F5를 눌러 CSS와 JavaScript를 새로 받습니다.

[ ] 자동완성 항목 클릭 시 해당 상세페이지로 이동한다.

DB와 업로드 폴더가 Git에서 제외되어 있기 때문입니다.
각자 테스트 데이터를 등록하거나, 필요한 비민감 테스트 자료만 별도 공유하세요.

4. 오류가 나왔을 때
============================================================

no such column: ...updated_at
  -> repair_udated_at.py 실행 여부와 완료 메시지를 확인하세요.

no such table: inquiries
  -> 문의 마이그레이션이 적용됐는지 확인하세요.

no such table: content_moderation 또는 moderation_log
  -> admin-init-db 실행 여부를 확인하세요.

no such column: user.profile_image 등 이 가이드에 없는 컬럼 오류
  -> 팀원 DB에 추가 차이가 있는 것입니다. 오류를 공유하고 보정을 요청하세요.

table ... already exists / duplicate column name
  -> 일부 구조가 이미 있습니다. 중단하고 DB 상태에 맞는 처리를 요청하세요.
  -> 실패 후 같은 명령을 무조건 반복하지 마세요.
  -> SQLite는 실패 전 일부 변경이 남을 수 있으므로 백업 복원 필요 여부를 확인하세요.

Can't locate revision / KeyError: 리비전번호
  -> 마이그레이션 파일 또는 이력이 맞지 않습니다. 받은 파일 목록을 확인하세요.

TemplateNotFound / ModuleNotFoundError
  -> 새 파일 누락, 잘못된 이름, 패키지 설치 문제를 확인하세요.

BuildError: Could not build url for endpoint
  -> 블루프린트 등록과 엔드포인트 이름을 확인하세요.

관리자 접근 403
  -> .env의 ADMIN_USER_ID, 실제 로그인 계정, admin-check를 확인하세요.

폼 제출 시 400 또는 요청 만료
  -> 페이지를 새로고침한 후 다시 로그인해 보세요.
  -> 계속 발생하면 CSRF 토큰과 SECRET_KEY 설정을 확인하세요.

화면이 예전 상태
  -> Ctrl+F5로 새로고침하세요.

- .env, DB, 백업 파일을 git add -f로 올리지 않기

6. 현재 상태에 대한 주의
============================================================

이 문서는 현재 프로젝트 파일 점검을 기준으로 작성했습니다.
모든 팀원 DB나 빈 DB의 업그레이드 성공을 보증하는 문서는 아닙니다.

# 어딧세이 코드로 배우는 Flask — 학습 교재

2026-10-02의 현재 작업 폴더를 기준으로 작성했습니다. 기준 커밋은 `fa1c206`이며, 아직 커밋하지 않은 내 여행지 화면의 CSS·템플릿 수정도 포함합니다. 코드가 바뀌면 이 문서의 설명과 줄 번호도 다시 확인하세요.

2. [실제 코드 찾아보기](02_코드지도.md)에서 함수와 라우트를 찾습니다.

하루 40~60분씩 7회에 나누는 것을 권합니다. 1회는 앱 구조, 2회는 조회·템플릿, 3회는 ORM, 4회는 로그인, 5회는 API·저장, 6회는 CSS, 7회는 Git·종합 복습입니다. 목표는 모든 파일을 외우는 것이 아니라, 화면에서 출발해 관련 코드까지 찾아가는 것입니다.

## 1. 이 프로젝트가 하는 일

사용자가 가입·로그인하고 여행지를 등록합니다. 여행지는 지도와 목록에 나타나고, 상세 화면에는 찜·리뷰·여행톡이 연결됩니다. 커뮤니티에는 별도의 게시글과 댓글·좋아요가 있습니다. 마이페이지의 내 여행지 목록은 로그인한 사람이 작성한 여행지만 보여줍니다.

| 역할 | 실제 위치 | 읽을 때 할 질문 |
|---|---|---|
| 앱 조립 | `odysay/__init__.py` | 어떤 Blueprint가 실제 등록됐나? |
| 설정 | `config.py` | DB 주소와 설정값은 어디서 오나? |
| 데이터 구조 | `odysay/models.py` | 어떤 컬럼이 다른 테이블을 가리키나? |
| 요청 처리 | `odysay/views/` | URL과 함수는 어떻게 연결됐나? |
| 입력 검증 | `odysay/forms.py` | 비어 있는 값과 중복 값은 어디서 걸러지나? |
| HTML 생성 | `odysay/templates/` | 어떤 변수를 서버가 전달하나? |
| 모양 | `odysay/static/css/` | HTML의 class와 선택자가 일치하나? |
| 브라우저 동작 | `odysay/static/js/` | 어떤 URL에 fetch를 보내나? |

`views`의 a0, a1 같은 파일명은 팀의 정리 방식입니다. Flask가 숫자 순서로 자동 실행하지 않습니다. 파일에 Blueprint가 있어도 앱에 등록되지 않으면 라우트가 활성화되지 않습니다. 예를 들어 `place_views.py`는 폴더에 있지만 현재 앱 팩토리의 등록 목록에는 없습니다.

## 2. 주소창에서 화면까지

내 여행지 페이지를 예로 들면 다음 순서입니다.

```text
GET /homepage/mypage/places
  → Flask가 등록된 URL 규칙을 찾음
  → auth_views.load_logged_in_user가 session으로 회원 조회
  → g.user에 이번 요청의 회원 저장
  → a5_mypage_views.my_places 실행
  → TripLocationmd를 user_id로 필터링
  → mypage_my_places.html에 places 전달
  → Jinja가 반복문을 실행하여 HTML 생성
  → 브라우저가 trip_list.css와 보조 CSS를 별도로 요청
  → 화면 표시
```

브라우저는 `.py` 파일을 직접 실행하지 않습니다. Flask는 완성된 HTML이나 JSON을 응답합니다. CSS는 DB에서 본인 여행지를 고르는 역할을 하지 않습니다. 서버 필터가 데이터 범위를 결정하고 CSS는 그 결과의 모양을 정합니다.

### Blueprint의 세 이름

`a5_mypage_views.py`의 Blueprint 이름은 `mypage`, URL 접두사는 `/homepage/mypage`, 함수 이름은 `my_places`입니다.

```python
bp = Blueprint('mypage', __name__, url_prefix='/homepage/mypage')

@bp.route('/places')
def my_places():
    ...
```

- 요청 주소: `/homepage/mypage/places`
- endpoint: `mypage.my_places`
- 템플릿 파일: `mypage_my_places.html`

이 셋은 서로 다른 이름입니다. `url_for('mypage.my_places')`는 endpoint를 실제 주소로 바꿉니다. `render_template('mypage_my_places.html')`는 파일을 찾아 HTML로 렌더링합니다. 둘을 바꿔 쓰면 `BuildError` 또는 `TemplateNotFound`를 만날 수 있습니다.

### 앱 팩토리

`create_app(test_config=None)`는 앱을 만들어 설정을 읽고 DB·CSRF·마이그레이션·Blueprint를 연결한 뒤 반환합니다. 테스트 설정은 일반 설정 다음에 적용됩니다. 그래서 실습에서는 실제 `odysay.db` 대신 메모리 DB를 지정할 수 있습니다.

`db = SQLAlchemy(...)`는 확장 객체를 만드는 단계이고 `db.init_app(app)`는 그 객체를 앱에 연결하는 단계입니다. 모델 import 자체가 실제 DB 테이블을 생성하지는 않습니다.

## 3. 본인 여행지만 조회하는 ORM

현재 `my_places()`의 핵심은 다음과 같습니다.

```python
places = (
    TripLocationmd.query
    .filter_by(user_id=g.user.id)
    .order_by(TripLocationmd.created_at.desc(), TripLocationmd.id.desc())
    .all()
)
```

| 표현 | 의미 |
|---|---|
| `TripLocationmd.query` | 여행지 상세 모델에 대한 조회 시작 |
| `filter_by(user_id=...)` | 작성자가 현재 회원인 행만 선택 |
| `created_at.desc()` | 등록 시간이 최신인 순서 |
| `id.desc()` | 등록 시간이 같은 경우 ID로 순서 결정 |
| `all()` | 조회 실행 후 결과를 리스트로 가져오기 |

개념적으로 아래 SQL과 같습니다. 실제 생성 SQL은 DB와 ORM에 따라 다를 수 있습니다.

```sql
SELECT * FROM trip_locationmd
WHERE user_id = :current_user_id
ORDER BY created_at DESC, id DESC;
```

로그인 검사가 먼저인 이유는 `g.user`가 없을 때 `.id`에 접근할 수 없기 때문입니다. `filter_by`를 지우면 다른 사람의 여행지까지 조회됩니다. 템플릿에서 버튼만 숨기는 것으로 데이터 접근 제한을 대신할 수 없습니다.

`first()`는 첫 객체 또는 None, `all()`은 리스트, `count()`는 개수입니다. `get_or_404(id)`는 찾지 못하면 404 응답을 발생시킵니다. 현재 코드에는 Query 방식이 많이 사용되며, 실습은 프로젝트에 있는 표현부터 이해하도록 구성했습니다.

## 4. 테이블과 관계 이해하기

현재 모델의 중심 연결은 다음과 같습니다.

```text
User ──작성자──> Uploadmd
                    ↑
          TripLocationmd.place_id
                    │
              TripLocationmd
               ├─ Bookmark
               ├─ Review
               ├─ TravelTalk ── TravelTalkComment
               └─ Comment.travel_place_id

User ──작성자──> Post
                ├─ Comment.post_id
                └─ PostLike
```

`Uploadmd`는 등록 정보를, `TripLocationmd`는 상세 화면 정보를 저장합니다. 두 모델에 장소 정보가 중복되어 있습니다. 이는 현재 구현의 특징이며 항상 권장되는 설계라는 뜻은 아닙니다. 한쪽만 수정하면 데이터가 달라질 수 있으므로 수정 라우트가 어느 모델을 갱신하는지 살펴보세요.

### 이름이 비슷한 ID 주의

- `TripLocationmd.id`: 상세 여행지 자체의 ID
- `TripLocationmd.place_id`: 연결된 `uploadmd.id`
- 상세 URL의 `place_id`: 현재 상세 뷰에서는 `TripLocationmd.id`를 조회하는 인자

따라서 URL 변수 이름과 DB 컬럼 이름이 같다고 같은 역할은 아닙니다. 두 테이블의 ID 값이 우연히 같아도 항상 같다고 가정하면 안 됩니다.

`ForeignKey('trip_locationmd.id')`는 DB 연결 규칙입니다. `relationship('TripLocationmd')`는 파이썬 객체 사이의 탐색 방법입니다. 현재 댓글은 `comment.travel_place`, 여행지는 `place.comments`로 연결됩니다. `Comment`는 일반 게시글 또는 여행지에 붙도록 두 외래키를 가지지만, 현재 모델에는 정확히 한쪽만 선택되도록 하는 CHECK 제약은 없습니다. 모델 구조와 업무 규칙을 구분해 읽어야 합니다.

`Bookmark`의 `(user_id, place_id)`와 `PostLike`의 `(user_id, post_id)`에는 고유 제약이 있습니다. 같은 사람이 같은 대상에 중복 행을 만들지 못하게 DB에서도 막습니다. 애플리케이션에서 먼저 조회하는 것과 DB 제약은 서로 보완합니다.

## 5. 저장: add, flush, commit, rollback

`a4_upload_views.upload()`의 저장 흐름은 다음과 같습니다.

```python
new_upload = Uploadmd(...)
db.session.add(new_upload)
db.session.flush()
new_trip_location = TripLocationmd(place_id=new_upload.id, ...)
db.session.add(new_trip_location)
db.session.commit()
```

`add`는 저장할 객체를 세션에 등록합니다. `flush`는 INSERT 등을 DB에 보내 자동 생성 ID를 얻지만 트랜잭션을 최종 확정하지 않습니다. `commit`이 저장을 확정합니다. 예외 후 `rollback`은 진행 중인 DB 트랜잭션을 되돌리고 세션을 다시 쓸 수 있게 합니다.

사진 파일 저장은 별도입니다. 현재 업로드 코드는 사진을 디스크에 먼저 저장한 뒤 DB 저장을 시도합니다. DB rollback이 이미 저장된 사진까지 자동 삭제하지 않습니다. 이 차이는 실패 상황을 설계할 때 중요한 복습 포인트입니다.

등록 성공 후 상세 페이지로 redirect합니다. 브라우저는 새 GET 요청을 보내 상세 HTML을 받습니다. POST 처리 결과로 화면을 직접 반환하는 것과 이동 응답을 주는 것은 서로 다른 흐름입니다.

## 6. 로그인: session과 g

`auth_views.login()`은 폼 검증, 회원 조회, 비밀번호 해시 검사, 활동 상태 검사를 수행합니다. 성공하면 `session.clear()` 후 `session['user_id'] = user.id`를 저장합니다.

다음 요청에서 `load_logged_in_user()`가 세션의 ID로 회원을 찾아 `g.user`에 넣습니다.

| 항목 | 수명과 역할 |
|---|---|
| `session['user_id']` | 요청 사이에 로그인 정보를 유지 |
| `g.user` | 이번 요청에서 사용할 회원 객체 |
| `password_hash` | 원문 비밀번호 대신 저장한 해시 |

Flask 기본 세션은 서명된 쿠키 방식입니다. 서명은 변조 검증용이며 암호화와 다릅니다. 세션에 비밀번호를 넣지 않습니다. `SECRET_KEY`는 세션 서명 및 CSRF 등에 중요합니다. 현재 설정 파일의 개발용 값은 배포용 비밀키 관리와 구분해야 합니다.

인증은 '누구인가', 권한 검사는 '이 데이터를 수정해도 되는가'입니다. 로그인했다고 다른 회원의 댓글을 수정할 수 있어서는 안 됩니다. 댓글 수정 함수에서 `comment.user_id`와 현재 회원 ID를 비교하는 부분을 찾아보세요.

## 7. HTML 응답과 JSON 응답

내 여행지는 서버가 Jinja 반복문으로 카드를 만듭니다. 여행지 목록은 HTML을 받은 뒤 JS가 데이터를 받아 카드를 만듭니다.

```text
내 여행지: GET → DB 조회 → render_template(places=...) → 카드가 있는 HTML
여행지 목록: GET → 기본 HTML → trip_list.js → fetch('/first/places') → JSON → DOM 카드
```

중요한 실제 연결: 현재 `trip_list.js`의 `loadTravelPlaces()`는 `/first/places`를 요청합니다. `/trip-list/places` API도 존재하지만 이 JS가 현재 호출하는 주소는 아닙니다. 파일 이름으로 추측하지 말고 fetch 문자열을 확인하세요.

`/first/places`는 위도·경도가 NULL이 아닌 여행지만 조회합니다. 반면 `/trip-list/places`는 모든 여행지를 조회합니다. 여행지가 DB에는 있는데 지도 연동 목록에서 빠졌다면 좌표 조건도 확인해야 합니다.

JSON 객체의 키와 JS에서 읽는 속성 이름이 연결 계약입니다. 서버가 `place`를 보내는데 브라우저가 `title`만 읽으면 이름이 표시되지 않을 수 있습니다. Network 탭에서 요청 URL, 상태 코드, Response를 함께 확인하세요.

찜·리뷰·여행톡은 `feature` Blueprint가 처리합니다. 상세 JS는 POST 요청에 JSON과 `X-CSRFToken`을 함께 보내는 부분이 있습니다. 전역 CSRF 보호가 있어도 `@csrf.exempt`가 붙은 커뮤니티 API는 예외입니다. '현재 구현'을 '모든 API가 보호된다'로 일반화하지 마세요.

## 8. 템플릿과 CSS: 이번 수정 이해하기

현재 내 여행지 템플릿은 먼저 `trip_list.css`, 다음 `mypage_my_places.css`를 불러옵니다. 공통 레이아웃은 첫 파일에서 재사용하고, 내 여행지 전용 요소만 두 번째 파일에서 보완합니다.

| HTML class | 하는 일 |
|---|---|
| `header`, `header-inner`, `gnb` | 상단 메뉴 구조 |
| `travel-hero` | 제목과 소개 영역 |
| `travel-container` | 본문 최대 너비와 여백 |
| `destination-grid` | 카드 열 배치 |
| `destination-card` | 카드 테두리·모서리·hover |
| `card-image`, `card-content` | 이미지와 텍스트 영역 |
| `my-list-actions`, `my-place-date` | 내 여행지 전용 기능 |

CSS를 링크하는 것만으로 같은 화면이 되지는 않습니다. HTML class가 CSS 선택자와 일치해야 합니다. 이전 템플릿의 `travel-card`에 `.destination-card` 규칙은 적용되지 않습니다.

공통 그리드는 기본 3열, 화면 너비 1000px 이하에서 2열, 520px 이하에서 1열입니다. CSS 캐스케이드는 중요도·선택자 구체성·선언 순서 등을 함께 고려합니다. 뒤에 읽은 파일이 모든 규칙을 무조건 덮어쓰는 것은 아닙니다.

공통 `.empty-state`는 JS 화면용으로 `display: none`입니다. 서버에서 빈 상태를 렌더링하는 내 여행지에는 `.my-places-page .my-empty-state { display: block; }`이 필요합니다. 같은 CSS를 재사용해도 화면 생성 방식의 차이는 보완해야 합니다.

Jinja의 `{{ ... }}`는 값 출력, `{% ... %}`는 조건·반복 같은 제어입니다. `photos`는 현재 쉼표로 구분한 파일명 문자열입니다. 템플릿이 split → trim → 빈 값 제거 → 첫 사진 선택 순서로 처리합니다. 사진이 없으면 자리 표시자를 출력합니다.

## 9. 오류를 찾는 순서

| 증상 | 먼저 볼 곳 | 확인 방법 |
|---|---|---|
| 404 | URL 규칙·Blueprint 등록 | routes 출력과 주소 비교 |
| 405 | GET/POST 허용 방식 | Network의 Request Method |
| BuildError | endpoint 오타 | url_for 인자와 routes 비교 |
| 400, CSRF 메시지 | 토큰 전달 | 폼 hidden 필드·요청 헤더 |
| 로그인으로 이동 | session, g.user | 302의 Location 확인 |
| no such table | 실제 DB 구조 | 모델과 DB는 별개인지 확인 |
| Could not resolve relationship | 모델 이름 | 이전 TravelPlace 참조 잔여 확인 |
| CSS가 안 바뀜 | 캐시·class·파일 경로 | 강력 새로고침·Computed 탭 |
| 목록이 비어 있음 | user_id·좌표·API | SQL 필터와 JSON 확인 |

권장 순서는 '요청이 서버에 도착했는가 → 어떤 함수가 받았나 → 조회 결과가 있나 → 응답이 올바른가 → 브라우저가 올바르게 표현했나'입니다. 여러 층을 동시에 수정하면 원인을 확인하기 어렵습니다.

## 10. 현재 코드와 문서를 구별해서 읽기

기존 README는 과거 통합본의 설명이 포함되어 있어 현재 코드와 일부 다릅니다. 업로드의 실제 저장 로직은 타임스탬프 파일명을 사용하며, README의 UUID·파일 검증 설명이 지금도 구현되어 있다고 단정할 수 없습니다. 실제 업로드 뷰는 Gemini 보정, 국내 TMAP 검색, Nominatim 대체 검색 흐름이 보입니다. 별도 services 코드가 있다고 현재 뷰가 반드시 그것을 호출하는 것은 아닙니다.

## 11. Git과 DB를 따로 생각하기

Git에는 작업 파일, stage(index), commit, 원격 브랜치가 있습니다. stash는 별도 보관함입니다. DB의 스키마와 레코드는 또 다른 상태입니다.

- `git add`: 이번 커밋에 담을 내용 선택. 서버로 보내지 않음.
- `git commit`: 로컬 이력 생성. 실행 중 앱의 DB를 변경하지 않음.
- `git push`: 커밋을 원격에 전달. PR 병합과는 별개.
- `git fetch`: 원격 정보를 갱신. 현재 파일은 자동 교체하지 않음.
- `git switch`: 다른 커밋의 파일로 전환. 미커밋 변경 때문에 막힐 수 있음.
- `git stash push -u`: 수정과 미추적 파일 보관. ignored DB는 포함되지 않음.
- `.gitignore`: 이미 추적 중인 파일의 추적을 자동 해제하지 않음.

PR은 특정 소스 브랜치에서 대상 브랜치로 변경을 검토·병합하는 요청입니다. 팀 저장소의 `pr-52`를 push해도 다른 사람의 포크 `ojh`를 소스로 하는 원래 PR이 자동 갱신되지는 않습니다.

이번에 겪은 큰 ZIP 오류는 최종 폴더에서 파일을 지우는 것만으로 해결되지 않을 수 있습니다. push 대상 이력에 큰 파일이 들어 있으면 그 커밋도 정리해야 합니다. 이미 공유된 이력은 팀과 협의 없이 재작성하지 않습니다.

모델을 수정하는 것과 실제 DB에 컬럼을 추가하는 것은 다릅니다. migration은 그 차이를 옮기는 절차입니다. 이 프로젝트는 사용자가 migration을 원격에서 제외하기로 했으므로, 팀원이 코드를 pull하는 것만으로 동일한 DB가 완성되지는 않습니다. 학습 실습은 별도 메모리 DB를 쓰며 실제 DB에 upgrade/reset을 수행하지 않습니다.
